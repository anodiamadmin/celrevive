## Setup Checklist

1. Open PowerShell in `celrevive_backend`:

```powershell
cd C:\Personal\celrevive\celrevive_backend
```

2. Create and activate a virtual environment:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
```

3. Install dependencies:

```powershell
python -m pip install --upgrade pip
pip install -r requirements.txt
```

4. Create `.env` from `.env.example` and configure:

```env
DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/celrevive
GEMINI_API_KEY=your-key-here
VISUAL_AI_MODEL=gemini-2.5-pro
SKIN_IMAGE_STORAGE_ROOT=./data/skin_images
```

5. Start PostgreSQL and create the `celrevive` database.

6. Run the attached DDL:

```powershell
psql -U postgres -d celrevive -f ..\architecture\database\CelRevive_DDL_updated.sql
```

7. Load the reference data, especially `skin_concern` rows:

```powershell
psql -U postgres -d celrevive -f ..\architecture\database\CelRevive_DML_Primary_Insert_updated.sql
```

8. Create at least one `customer_session` row with status `STARTED` and consent enabled. The upload route currently requires its UUID as the multipart `session_id` field.

9. Start the backend:

```powershell
uvicorn app.main:app --reload
```

10. Test the endpoint using the session UUID:

```powershell
curl.exe -X POST "http://127.0.0.1:8000/api/v1/image-validation" `
  -F "session_id=YOUR_SESSION_UUID" `
  -F "image=@C:\path\to\valid-image.jpg"
```

11. Confirm a successful response contains:

```json
{
  "valid": true,
  "image_id": "...",
  "next_step": "questionnaire"
}
```

12. Verify:
- The image exists under `data/skin_images`.
- `skin_image` contains the metadata row.
- `customer_session.session_status` becomes `IMAGE_RECEIVED`.
- The background task sends the image to Gemini.
- `session_skin_concern_detection` receives all 28 concern rows.

13. Run tests after installation:

```powershell
python -m pytest -q
```

The questionnaire template is currently only a corrected JSON artifact. Questionnaire processing is not part of the implemented 1.1–2.5 image-analysis flow.

ASYNC WORKFLOW CHANGES

Implemented the asynchronous image-analysis handoff in celrevive_backend/.

POST /api/v1/image-validation validates and saves the image, queues analysis, and returns next_step: "questionnaire" on success. Validation runs in a threadpool so image processing doesn’t block the event loop. See image.py.
The old POST /api/v1/image-analysis path remains as a deprecated async alias and returns 202 Accepted instead of waiting for analysis.
GET /api/v1/sessions/{session_id}/analysis reports pending, processing, completed, or failed; completed results include detected concerns. See sessions.py.
The worker records success or failure in the session status in visual_ai_task.py. I also updated dev_doc with the client flow.

Added POST /api/v1/create-session in sessions.py, registered it in main.py, and defined its request/response models in customer_session.py.

The endpoint creates a STARTED session using the supplied Shopify details, requires explicit consent, and returns the generated session_id. Shopify details are request data rather than hard-coded sample values; notes default to “Customer session initiated with consent.”


final update:

skin_concern_display_name added in table skin_concern


POST /api/v1/create-session	Start the flow after the customer has provided the required consent. Send JSON containing consent_given: true and any available Shopify identifiers. Save the returned session_id.
POST /api/v1/image-validation	Upload the image as multipart form data with fields image and session_id. Use the ID returned by session creation. This is the endpoint the frontend should use for image upload.
GET /api/v1/sessions/{session_id}/analysis	Poll after upload using that same ID. Continue on pending or processing; show results on completed; handle the two failure statuses separately.
GET /health	Optional backend readiness check; not part of the customer flow.
POST /api/v1/image-analysis is a deprecated upload alias; use /image-validation for new integration. There is no /api/v1/recommendation/{session_id} route in the current backend.
